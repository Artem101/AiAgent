# Разработка

## Проверки перед коммитом

```bash
cargo fmt --check                    # rustfmt.toml: max_width = 120
cargo clippy --all-targets           # должно быть 0 предупреждений
cargo test                           # 26 тестов, ~5 с без учёта компиляции
cargo build --release --examples     # примеры компилируются
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps   # нет битых ссылок в rustdoc
```

В `dev`-профиле зависимости (candle, gemm) собираются с `opt-level = 3`, поэтому тесты с
обучением идут быстро и без `--release`.

## Инварианты

Любое изменение должно сохранять три свойства. Все три проверяются тестами.

### 1. Паритет graph ↔ kernel

У модуля две реализации: `forward` на candle (для обучения) и упакованная версия (для инференса).
Меняя одну, меняйте и другую, и держите тест паритета зелёным. Порядок полей модуляции,
константы (`LN_EPS`, `L2_EPS`, масштаб времени 1000) и раскладка весов `[out, in]` общие для
обоих путей. Тест векторного поля намеренно заполняет веса случайными значениями, потому что
нулевая инициализация adaLN-Zero спрятала бы ошибки.

### 2. Ноль аллокаций в горячем пути

В функциях горячего пути нельзя:
* `Vec::new`/`vec!`/`collect`/`to_vec`/`format!`/`String`;
* операции candle, создающие тензоры (любая арифметика тензоров, `to_dtype`, `copy`, `narrow` с
  последующей материализацией);
* `Box::new`, клонирование `Vec`.

Можно:
* ядра из `kernels` на срезах;
* функции `kernels::inplace`;
* клонирование `Tensor` (это `Arc`, без аллокации);
* `Rng::stream`;
* `Instant::now`.

Новые буферы добавляются в соответствующий workspace и выделяются через `Arena` при его создании.
Если новый код вызывается из `generate_into`, `tests/zero_alloc.rs` его уже покрывает.

### 3. Детерминизм

Случайность берётся только из `Rng` с потоком, привязанным к индексам работы: номер итерации,
сэмпла и т.п. Порядок суммирования не должен зависеть от разбиения работы между потоками:
каждый выход считает один поток, а редукции по сэмплам идут последовательно.

## Рецепты

### Новая задача

`src/data.rs`:

1. добавить вариант в `enum Task`;
2. добавить ветку в `Task::parse` (имя для `--task`) и `Task::name`;
3. реализовать ответ в `Task::apply`.

Если ответ имеет другую длину, чем промпт, ослабьте проверку в `TaskSampler::new`. Модель и
движок по построению допускают `N ≠ L` (таблица позиций имеет длину `N + L`), но это не покрыто
тестами. CLI (`--len`) предполагает `N = L`.

### Новый ODE-решатель

`src/flow/ode_solver.rs`:

1. вариант в `SolverKind` плюс ветки в `parse` и `evals_per_step`;
2. ветка в `FlowMatchingSampler::integrate`. Используйте только `axpy_`/`lincomb_`/`acc_lincomb_`
   и буферы `SamplerBuffers`. Если нужен ещё один буфер скорости, добавьте поле в
   `SamplerBuffers`: оно выделится из арены;
3. та же схема в батчевом `flow::sample_graph` для оценки;
4. строка с допуском в `solvers_converge_with_expected_order`.

### Своё векторное поле или другой декодер

Реализуйте `VectorFieldEstimator` (см. [api.md](api.md#ode-сэмплер-и-собственное-векторное-поле)).
Всё, что не зависит от `t`, считайте в `prepare`. Буферы держите в самом типе и выделяйте из
`Arena` при создании.

### Своя энергия планировщика

Энергия задана в `JEPAPlanner::energy(terminal, goal, actions)` и повторена в
`GradientPlanner::refine` (graph-версия для latent GD). Меняйте обе. Если энергии нужна вся
траектория, а не только конец, передайте в `energy` срез `st` целиком — он уже есть в
замыкании `simulate`.

### Новое ядро

1. Функция на срезах в `src/kernels/mod.rs`. Выход и scratch передаются параметрами.
2. Если нужен SIMD, код идёт в `simd.rs`: `unsafe fn` с `#[target_feature]`, безопасная обёртка с
   runtime-проверкой и переносимый фолбэк. Тест сравнивает оба пути.
3. Если работа может быть крупной: `if parallel_for(work) { par_… } else { … }`, с одинаковым
   порядком суммирования для каждого выхода.

### Изменить архитектуру модуля

1. Параметры: `ParamStore::{linear, linear_zero, mlp, tensor}`. Имена должны быть уникальны — они
   же ключи чекпойнта.
2. `forward` на candle.
3. Упакованная версия: `pack(dtype)` и вычисление в workspace.
4. Тест паритета.
5. Старые чекпойнты станут несовместимы: `import` сообщит о недостающем ключе.

### Новый пресет

Функция рядом с `EngineConfig::tiny`/`small` и ветка в `EngineConfig::preset`. CLI подхватит его
по `--preset`.

## Стиль кода

* Ошибки: `candle_core::Result` и `bail!`. Паники допустимы только при нарушении контракта
  программистом (`assert!` длин в `dot4`) и при отравленном mutex `VarMap`.
* `unsafe` — только в `kernels/simd.rs`, и у каждой функции есть комментарий `# Safety`.
* Комментарии объясняют «почему» и формулы. Главные формулы модуля стоят в doc-комментарии его
  `mod.rs`.
* Публичные типы состояний — только через NewType из `types.rs`.

## Известные ограничения

| Ограничение | Почему / что можно сделать |
|---|---|
| CUDA не проверялась | в среде разработки не было GPU. Graph path device-generic, ядра — только CPU. Следующий шаг — CUDA-ядра для `InplaceOp` (`cuda_fwd`) через cudarc |
| Обучение в bf16 на CPU невозможно | в candle 0.11 нет CPU-matmul для bf16; f16 работает, но медленнее f32 |
| Только TTT-Linear | TTT-MLP (двухслойные быстрые веса) не реализован |
| Инференс по одному запросу | ядра рассчитаны на `B = 1`. Для батча нужны workspace'ы на `B` запросов или пул движков |
| Задачи требуют `N = L` | ограничение генератора данных, не модели |
| Политика обучена только на teacher-траекториях | классическая проблема накопления ошибки; DAgger-подобное дообучение на собственных роллаутах должно сократить разрыв с оракулом |
| Позиционная таблица конечна | позиции за её пределами используют последнюю строку; для длинных контекстов нужны относительные позиции или их отсутствие |
