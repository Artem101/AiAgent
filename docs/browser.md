# Агент-браузер

`cog_engine` умеет искать информацию в настоящем браузере. Модель смотрит на страницу в
headless Chromium, решает, что сделать (ввести запрос, нажать кнопку, открыть ссылку, вернуться
назад), браузер выполняет действие, и так до тех пор, пока модель не даст ответ.

```
  вопрос ──► Goal (товар, атрибут)
                 │
   ┌─────────────▼──────────────────────────────────────────────────────────────────┐
   │  Chromium ──DOM-снимок──► наблюдение (24 токена) ──► CognitiveEngine            │
   │     ▲                     [head] results [input] lamp …    TTT → JEPA → CFM     │
   │     │                     … <goal> lamp price                                   │
   │     └── click / type / back ◄── действие [verb, role, word, <end>] ◄────┘       │
   └──────────────────────────────── … пока не ANSWER ──────────────────────────────┘
```

Код лежит в `src/browser/`. Проверки: `tests/browser.rs`.

## Быстрый старт

```bash
cargo build --release

# готовая модель уже лежит в models/browser_agent.safetensors; обучить свою (~12 мин на одном ядре):
RAYON_NUM_THREADS=1 ./target/release/cog_engine train --task browser --steps 8000 --out agent.safetensors

# задать вопрос: агент сам откроет Chromium, найдёт товар и прочитает ответ со страницы
./target/release/cog_engine agent --ckpt models/browser_agent.safetensors --question "Сколько стоит лампа?"

# успешность на 100 случайных задачах в настоящем Chromium
./target/release/cog_engine agent-eval --ckpt models/browser_agent.safetensors --browser chrome --episodes 100

# посмотреть «мини-интернет» глазами: откройте http://127.0.0.1:8080/w/42/ в своём браузере
./target/release/cog_engine site --addr 127.0.0.1:8080
```

Chromium ищется так: переменная `COG_CHROME`, затем Chromium из Playwright
(`$PLAYWRIGHT_BROWSERS_PATH/chromium`, `/opt/pw-browsers/chromium`), затем `chromium`,
`chromium-browser`, `google-chrome` в `PATH`. На своей машине добавьте `--headed`, чтобы видеть
окно браузера, пока агент работает.

Пример вывода `agent` (обученный чекпойнт, Chromium, мир 42):


## Песочница: «мини-интернет»

Агент работает с сайтом, который поднимает сам `cog_engine` (`src/browser/world.rs`,
`src/browser/server.rs`): поисковик по каталогу из 24 товаров.

| Страница | URL | Что на ней |
|---|---|---|
| поиск | `/w/{мир}/` | заголовок, поле ввода, кнопка `search` |
| результаты | `/w/{мир}/search?q=lamp` | поле с запросом, 4 ссылки на товары (точное совпадение среди случайных), ссылка `home` |
| товар | `/w/{мир}/item/lamp` | заголовок, ссылка `home`, таблица `price`/`color`/`brand`/`rating` в случайном порядке |

**Факты случайные и зависят от номера мира.** Цена, цвет, бренд и рейтинг каждого товара, а
также порядок строк таблицы берутся из генератора с сидом мира. Поэтому модель не может
запомнить ответы: в каждом мире лампа стоит по-разному, и ответ нужно найти и прочитать. Цены
(1…20) и рейтинги (1…5) пересекаются, так что нельзя взять «какое-нибудь число со страницы»,
нужна именно строка нужного атрибута.

Почему не настоящий интернет: у модели ~340 тыс. параметров и закрытый словарь из 84 токенов, а
у среды, где она работает, нет открытого доступа в сеть. Сам браузерный слой (`Chrome`, CDP,
снимки DOM, клики, ввод) от сайта не зависит, а о том, что нужно для других сайтов, — в разделе
[Ограничения и как расширять](#ограничения-и-как-расширять).

## Наблюдение

`src/browser/obs.rs`. Скрипт в странице (`Runtime.evaluate`) собирает видимые элементы
`h1, p, a, input, button, th, td` в порядке документа и помечает их атрибутом `data-aid`.
Каждый элемент становится токеном роли и словами текста (у поля ввода — его значение или
`<empty>`). Незнакомые слова превращаются в `<unk>`. Страница занимает первые 21 позицию, цель —
всегда последние три:

```
[head] lamp [link] home [label] brand [value] delta [label] price [value] 10 [label] color [value] blue [label] rating [value] 5 <goal> lamp price
└────────────────────────────── страница (≤ 21 токен, дополняется <pad>) ──────────────────────────────────────────────┘ └─── цель ───┘
```

Цель стоит в конце намеренно: так её токены работают как запросы к странице, уже записанной
в `W_fast` (см. [Архитектура](#что-пришлось-изменить-в-движке)).

## Действия

Модель выдаёт `L = 4` токена параллельно (как любой ответ `cog_engine`):

| Действие | Токены | Что делает браузер |
|---|---|---|
| ввести текст | `TYPE [input] lamp <end>` | фокус на первое поле, очистить, `Input.insertText` |
| нажать кнопку | `CLICK [button] search <end>` | настоящий клик мышью (`Input.dispatchMouseEvent`) в центр элемента с таким текстом |
| открыть ссылку | `CLICK [link] lamp <end>` | то же для ссылки |
| назад | `BACK <none> <none> <end>` | переход на предыдущую запись истории |
| ответить | `ANSWER <none> 10 <end>` | конец эпизода |

Элемент выбирается по видимому тексту, как `getByText` в Playwright. Если такого элемента на
странице нет или токены не складываются в действие, шаг считается ошибочным и эпизод
продолжается.

## Обучение

### Учитель

`src/browser/expert.rs` — сценарий, который по одному только наблюдению выдаёт оптимальное
действие:

```
страница нужного товара             → ANSWER <значение из строки нужного атрибута>
страница другого товара             → BACK
нужный товар среди ссылок           → CLICK [link] <товар>
в поле уже набран нужный товар      → CLICK [button] search
на странице есть поле поиска        → TYPE [input] <товар>
иначе                               → BACK
```

Учитель решает любую задачу за 4 шага (`tests/browser.rs` проверяет 300 эпизодов) и выходит из
любого состояния: неверный запрос, не та страница, пустая или ошибочная страница. Так как он
смотрит только на токены, он же служит целевой функцией задачи: `Task::Browser.apply(prompt)`.

### Данные

`src/browser/data.rs` (`--task browser`). Это behaviour cloning, но на широком распределении
состояний, а не только на 4-шаговых траекториях учителя. Кроме «правильных» состояний в данные
попадают набранный, но не отправленный запрос, неверный запрос, не та страница товара и
страница 404. Благодаря этому модель учится исправлять и свои ошибки (идея DAgger). Каждый
пример — новый мир, так что данные бесконечны и не повторяются.

Страницы для обучения строит симулятор (`src/browser/sim.rs`), без HTML и сети: генерация
данных почти ничего не стоит, обучение идёт ~11 шагов в секунду на одном ядре. Тест `simulator_matches_chromium` сверяет его с Chromium: на целых эпизодах,
с вводом текста и переходами назад, снимки совпадают элемент в элемент. Поэтому модель,
обученная на симуляторе, видит в настоящем браузере те же входы.

### Что пришлось изменить в движке

С исходной архитектурой агент уверенно различал типы страниц (глагол действия верен в 97–99%),
но плохо переносил слова: товар из цели копировался в 64–77% случаев, а значение из таблицы
выбиралось наугад среди четырёх строк (25%). Изолированный эксперимент показал, что дело не в
энкодере. TTT-энкодер с линейной головой, обученный напрямую предсказывать слово действия,
читает значение из таблицы с точностью 91%, а с окном и readout (ниже) — 100%. Проблема была в
обучающем сигнале. Декодер учится на «учительском» плане, латентные действия которого выводятся
из будущих состояний, уже содержащих ответ. Энкодеру остаются только слабые MSE-потери в
латентном пространстве, и сигнала «вытащи ответ из страницы» он почти не получает.

Три изменения, все опциональные: по умолчанию выключены, так что задачи `sort/reverse/copy` и
старые чекпойнты не меняются.

1. **Проба ответа** (`jepa.probe_weight`, для браузера 1.0). Линейная голова требует, чтобы
   начальное латентное состояние декодировалось в токены ответа: `CE(Linear(s_0) → ответ)`.
   Энкодер получает прямой сигнал, а информация оказывается в `s_0` — там, откуда её берут цель
   `ĝ`, политика π и декодер. Голова используется только при обучении и в упакованный движок не
   попадает.
2. **Короткая каузальная свёртка в TTT** (`ttt.conv_width`, для браузера 4). В TTT-Linear ключ,
   значение и запрос токена считаются только из самого токена, и одно обновление быстрых весов
   не может связать `price` со стоящим через токен `10`. Теперь `k, v, q, η` токена `t`
   считаются из окна `[LN(x_t); LN(x_{t−1}); …; LN(x_{t−w+1})]`, как короткая свёртка перед
   TTT/Mamba-слоями. На ячейке значения окно `[10, [value], price, [label]]`, и `W_fast`
   запоминает связь «атрибут → значение».
3. **Readout последних выходов** (`ttt.readout_last`, для браузера 3). В `S_prompt` добавляются
   выходы `z_N, z_{N−1}, z_{N−2}` трёх токенов цели. Каждый `z_t = W_t q_t` — ассоциативный
   поиск по странице, уже записанной в `W_fast`: запрос `price` достаёт значение из строки
   `price`.

Оба пути исполнения меняются синхронно. Паритет graph ↔ kernel проверяет
`ttt::packed_encoder_matches_graph` (вариант с окном 3 и readout 2), ноль аллокаций —
`tests/zero_alloc.rs` (браузерная конфигурация целиком).

**Абляции** (`tiny`, 3000 шагов, одинаковый протокол `agent-eval --steps 1000 --episodes 200
--seed 99` в симуляторе):

| Окно + readout | Проба | План π | Шаги верно | ANSWER верно | Эпизоды успешно |
|:---:|:---:|:---:|---:|---:|---:|
| – | – | – | 57.4% | 25.5% | 33.5% |
| ✓ | – | – | 46.2% | 9.2% | 10.5% |
| ✓ | – | ✓ | 53.9% | 17.6% | 21.0% |
| – | ✓ | – | 93.3% | 84.3% | 88.5% |
| – | ✓ | ✓ | 90.5% | 76.1% | 75.0% |
| **✓** | **✓** | **–** | **96.3%** | **91.1%** | **96.5%** |
| ✓ | ✓ | ✓ | 90.8% | 76.6% | 79.0% |

* Главный вклад даёт проба: 33.5% → 88.5%.
* Окно и readout без пробы только мешают: больший readout труднее обучить через слабый сигнал. С
  пробой они добавляют 8 пунктов: 88.5% → 96.5%, ответ верен в 91% против 84%.
* «План π» — проверенная и отвергнутая идея. Для части примеров декодер кондиционировался на
  плане инференса `[s_0, роллаут π к ĝ]` вместо учительского. Во всех сочетаниях это ухудшало
  результат, поэтому в код опция не вошла.

## Результаты

Модель `models/browser_agent.safetensors`: пресет `tiny` с окном, readout и пробой, 353 781
параметр, 8000 шагов AdamW с batch 64 (`RAYON_NUM_THREADS=1 cog_engine train --task browser
--steps 8000`, сид 7). Обучение заняло 11.6 мин на одном ядре CPU. С четырьмя потоками rayon
выходит медленнее, 17 мин: для модели такого размера накладные расходы потоков больше выигрыша.

Все задачи новые: мир и вопрос каждой задачи случайные, при обучении они не встречались.

| Где | Задач | Успех | Неверный ответ | Без ответа | Шагов на задачу | Время на задачу |
|---|---:|---:|---:|---:|---:|---:|
| **Chromium** | 500 | **98.2%** | 8 | 1 | 4.06 | 122 мс (решения модели — 5.8 мс на шаг) |
| симулятор | 1000 | 98.3% | 14 | 3 | 4.09 | 24 мс |

Точность отдельных шагов на 2000 случайных состояниях — 98.7%:

| Действие учителя | Точно | Верный глагол |
|---|---:|---:|
| `CLICK` (ссылка или кнопка) | 99.7% | 99.8% |
| `TYPE` | 97.6% | 97.6% |
| `BACK` | 98.3% | 98.3% |
| `ANSWER` (прочитать значение из таблицы) | 98.7% | 99.9% |

Ошибочные шаги (2% — клик по отсутствующему тексту и т.п.) агент в основном исправляет сам, отсюда
4.09 шага на задачу вместо 4.

Разброс между запусками обучения заметный. С той же конфигурацией и сидом 8 получилось 93.7% на
тех же 1000 задачах в симуляторе. Вариант с отвергнутым «планом π» (сид 7) дал 96.1%. В
репозитории лежит лучшая из трёх моделей; она воспроизводится командой выше при одном потоке
rayon.

Инференс (`cog_engine bench --ckpt models/browser_agent.safetensors`): веса 658 KiB (bf16), арена
217 KiB, `W_fast` 4 KiB; один шаг агента — encode 79 µs + plan 2.7 ms + decode 2.0 ms, 210
решений в секунду. Остальное время эпизода уходит на Chromium: загрузку страниц и снимки DOM.

## Программный интерфейс

```rust
use cog_engine::browser::{self, agent, Chrome, EnginePolicy, Goal, SiteServer};
use cog_engine::{CogModel, CognitiveEngine};

let model = CogModel::new(browser::engine_config("tiny")?, &candle_core::Device::Cpu)?;
model.load("models/browser_agent.safetensors")?;
let mut policy = EnginePolicy::new(CognitiveEngine::from_model(&model)?);

let site = SiteServer::start("127.0.0.1:0")?;          // песочница
let mut chrome = Chrome::launch_default()?;            // headless Chromium
let goal = Goal::parse("какого цвета велосипед")?;     // русский или английский вопрос
let ep = agent::run_episode(&mut chrome, &mut policy, &site.origin(), 42, goal, 10, |step| {
    println!("{} → {:?}", step.url, step.action);
})?;
println!("ответ: {:?}, верно: {}", ep.answer.map(browser::vocab::token_str), ep.success());
```

Любой браузер подключается через трейт `Browser` (`goto`, `snapshot`, `click`, `type_text`,
`back`), любая политика — через `Policy` (наблюдение → токены действия). `ExpertPolicy` —
учитель, `EnginePolicy` — обученный движок.

## Как устроено управление Chromium

`src/browser/chrome.rs`, `src/browser/cdp.rs`, без новых тяжёлых зависимостей (добавлен только
`serde_json`, он уже был в дереве зависимостей через `safetensors`):

* Chromium запускается с `--headless=new --remote-debugging-port=0` и временным профилем.
  Адрес DevTools читается из stderr, вкладка ищется через `/json/list`.
* Протокол — собственный минимальный WebSocket-клиент (RFC 6455: handshake, маскирование,
  фрагменты, ping/pong) поверх `TcpStream` и JSON-RPC CDP.
* Навигация: `Page.navigate` и ожидание `Page.loadEventFired`. После клика ждём начала навигации
  (`Page.frameRequestedNavigation`/`frameStartedLoading`) и загрузки. Назад:
  `Page.getNavigationHistory` + `Page.navigateToHistoryEntry`. Back/forward cache выключен,
  поэтому возврат всегда даёт загрузку страницы.
* `--no-sandbox` включён по умолчанию (`ChromeOptions::no_sandbox`): без него Chromium не
  запускается от root в контейнере.

## Ограничения и как расширять

* **Словарь закрыт.** Модель знает 84 токена: 24 товара, 4 атрибута, 8 цветов, 8 брендов, числа
  1…20 и служебные слова. Вопрос разбирается по ключевым словам (`Goal::parse`, английский и
  русский). Страница с незнакомыми словами превратится в `<unk>`.
* **Сайт синтетический.** Настоящие сайты длиннее 21 токена и устроены иначе. Чтобы агент
  работал на других сайтах, нужны: новые слова в `vocab.rs`, новые типы страниц в `world.rs`
  (или реальные страницы в Chromium), расширенный учитель и больший `OBS_LEN`. Скорее всего,
  понадобится и пресет `small`.
* **Один ответ — одно слово.** Действие — 4 токена. Для длинных ответов увеличьте
  `ACTION_LEN` (он должен делиться на горизонт планирования 4).
