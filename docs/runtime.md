# Рантайм: память, точность, SIMD, параллелизм, скорость

Этот документ про kernel path — то, что исполняется внутри `CognitiveEngine`.

## Модель памяти

### Арена

Все буферы инференса создаются **один раз**, в `CognitiveEngine::from_model`, через `Arena`
(`src/arena.rs`):

| Метод | Что выдаёт | Для чего |
|---|---|---|
| `arena.tensor(shape)` | нулевой f32-тензор candle с **собственным** storage | состояния на границах модулей: `W_fast`, `S_prompt`, `s_0`, `ĝ`, план, `X_t`, скорости |
| `arena.host(len)` | `Box<[f32]>` фиксированного размера | scratch внутри ядер: активации, K/V, скоры внимания, буферы MPPI |
| `arena.host_u32(len)` | `Box<[u32]>` | токены |

`Box<[f32]>` не может вырасти. Код, которому передали только такие срезы, реаллоцировать не
способен физически. Арена считает байты и число буферов, это видно в `CognitiveEngine::memory()`.

Workspace'ы по модулям:

| Workspace | Где | Содержимое |
|---|---|---|
| `TttWorkspace` | `ttt/mod.rs` | `x, x̃, k, v, q, z, Σz`, вход readout, скрытый слой, `W_fast`, `S_prompt` |
| `MppiWorkspace` | `jepa/planner.rs` | действия и состояния всех `M` роллаутов, стоимости, веса, номинал, лучший сэмпл, буферы политики, план |
| внутренний workspace `PackedVectorField` | `flow/vector_field.rs` | `h, a, q, k, v`, выход внимания, MLP, K/V плана на каждый слой, скоры |
| `SamplerBuffers` | `flow/ode_solver.rs` | `X`, промежуточная точка, две скорости |

### Изменение тензоров candle на месте

Тензоры candle логически неизменяемы: каждая операция создаёт новый тензор. Чтобы писать в
заранее выделенные тензоры, используются кастомные операции candle `InplaceOp1/2/3`. Они получают
`&mut CpuStorage` под блокировкой записи, и ядро пишет прямо в storage (`src/kernels/inplace.rs`):

| Функция | Действие |
|---|---|
| `host_read(t, \|s: &[f32]\| …)` | читать тензор как срез |
| `host_write(t, \|s: &mut [f32]\| …)` | писать в тензор как в срез |
| `copy_from_slice(t, src)` | скопировать срез в тензор |
| `axpy_(y, α, x)` | `y ← y + αx` |
| `lincomb_(y, a, x₁, b, x₂)` | `y ← a·x₁ + b·x₂` |
| `acc_lincomb_(y, a, x₁, b, x₂)` | `y ← y + a·x₁ + b·x₂` |
| `fill_normal_(t, rng, σ)`, `fill_(t, v)` | заполнить шумом или константой |

Быстрый путь срабатывает для contiguous f32-тензоров на CPU (`is_host_f32`). Для других устройств
и типов функции с суффиксом `_` делают то же самое операциями candle и **перепривязывают**
`&mut Tensor` на новый тензор. Результат правильный, но с аллокацией. Так сэмплер и
`FastWeightsState` работают на любом устройстве, а на CPU не аллоцируют.

**Правило алиасинга.** Изменяемый тензор не должен делить storage со входом той же операции:
блокировка записи и чтения на одном `RwLock` приведёт к дедлоку. Буферы арены всегда разные.

**Следствие для пользователя.** `PromptState` и `LatentPlan`, которые возвращают `encode` и
`think`, — это ссылки на тензоры движка. Следующий запрос их перезапишет. Чтобы сохранить,
нужна копия (`tensor().copy()`).

## Гарантия «ноль аллокаций»

**Что гарантируется.** После создания движка и workspace'ов следующие вызовы не обращаются к
аллокатору кучи:

* `FastWeightsState::step_update` (и весь `PackedTttEncoder::encode`);
* `JEPAPlanner::plan_into`, включая роллаут политики;
* `FlowMatchingSampler::sample_into` / `integrate` с `PackedVectorField`;
* `CognitiveEngine::generate_into`, `encode`, `think` (в режиме `Mppi`) и `decode`.

**Как проверяется** (`tests/zero_alloc.rs`). Тест подменяет глобальный аллокатор на считающий.
В бинаре один тест, поэтому соседние тесты не мешают. Каждую операцию он прогревает одним
вызовом, затем замеряет повторный. Проверяются два режима: последовательные ядра и работа
внутри пула rayon из 4 потоков. Перед замером все потоки пула принудительно запускаются через
`pool.broadcast`, потому что старт потока аллоцирует.

**Что аллоцирует (и это ожидаемо):**

* создание: `from_model`, `workspace`, `pack`, `Arena::*`;
* удобные обёртки: `generate` (возвращает `Vec`), `JEPAPlanner::plan`, `FlowMatchingSampler::sample`,
  `VectorFieldEstimator::estimate_velocity`, `FastWeightsState::forward`;
* режим `PlannerKind::MppiThenGradient`: latent GD строит небольшой граф autograd candle;
* весь graph path (обучение, `decode_graph`, `GraphVectorField`);
* пути ошибок (строка сообщения, backtrace).

**Оговорка про rayon.** Если параллельное ядро вызвано из потока **вне** пула rayon, rayon кладёт
задачу в глобальную очередь-инжектор. Та изредка выделяет новый блок: амортизированно, примерно
раз в 63 вызова. Для строгой гарантии вызывайте движок изнутри пула:

```rust
let pool = rayon::ThreadPoolBuilder::new().num_threads(4).build().unwrap();
pool.broadcast(|_| ());                                  // запустить все потоки заранее
pool.install(|| engine.generate_into(&prompt, seed, &mut out))?;
```

Или выключите распараллеливание: `kernels::set_parallel(false)`. Результаты от этого не меняются.

## Точность

| Где | Тип |
|---|---|
| Упакованные веса инференса | `bf16` по умолчанию (`EngineConfig::weight_dtype`; также `f16`, `f32`) |
| Активации, аккумуляторы скалярных произведений, LayerNorm, softmax | `f32` |
| `W_fast` (это аккумулятор градиентных шагов) | `f32` |
| Состояние ODE `X_t`, скорости, шаги интегратора | `f32` |
| Мастер-веса и моменты AdamW при обучении | `f32` |
| Прямой/обратный проход при обучении | `TrainConfig::compute_dtype`: f32 на CPU, bf16 на CUDA по умолчанию |

bf16 → f32 — это сдвиг 16 бит влево, потерь нет. Округление происходит только один раз, при
упаковке. Тесты паритета допускают отклонение ≤ 5% от масштаба выхода для bf16 и ≤ 1e-3
абсолютно для f32-упаковки.

## SIMD

Весь `unsafe` крейта находится в `src/kernels/simd.rs`.

| Функция | Что считает | Путь x86-64 | Фолбэк |
|---|---|---|---|
| `dot_f32(a, b)` | `Σ aᵢbᵢ` | AVX2 + FMA, 2 аккумулятора × 8 полос | 8 скалярных аккумуляторов |
| `dot_bf16(w, x)` | то же, веса bf16 | `vpmovzxwd` + сдвиг → FMA | конвертация `half` |
| `dot_f16(w, x)` | то же, веса f16 | F16C `vcvtph2ps` → FMA | конвертация `half` |
| `dot4_*(w[4], x)` | 4 скалярных произведения с общим `x` | одна загрузка `x` на 4 FMA | 4 × `dot` |

Возможности процессора проверяются при каждом вызове через `is_x86_feature_detected!` (внутри
кэшируется, это одна атомарная загрузка). Функции с `#[target_feature]` вызываются только после
проверки. Длины срезов проверяются в безопасной обёртке. Какой путь выбран, показывает
`kernels::simd::simd_level()` (печатается в `demo`/`train`).

### Линейный слой (`PackedLinear::forward`)

Веса хранятся в раскладке candle `[out, in]`. Выход делится на блоки по `bs ∈ {64, 32, 16, 8, 4}`
выходов одной строки (`bs` делит `d_out`). Внутри блока выходы считаются четвёрками через `dot4`.
Блок — единица работы rayon. На весах bf16 это даёт ≈ 10 GMAC/s на ядро против 4.4 GMAC/s у
наивного «один выход — одно скалярное произведение».

### Остальные ядра (`src/kernels/mod.rs`)

`layer_norm_rows` (ε = 1e-5), `modulate_rows` (adaLN), `attention` (задача = пара «запрос × голова»,
у каждой своя строка scratch под скоры), `softmax_inplace`, `rank1_update` (фьюзнутый шаг TTT),
`matvec_f32`, `sinusoidal_embedding`, поэлементные `gelu`/`silu`/`fast_tanh`.

`fast_tanh` — рациональная minimax-аппроксимация `x·P(x²)/Q(x²)`, насыщение за `|x| ≈ 8`, ошибка
< 5e-7. В ней нет вызова libm, поэтому циклы векторизуются. Через неё считаются GELU и tanh
политики. Graph path использует точный tanh candle; расхождение пренебрежимо и покрыто тестами
паритета.

## Параллелизм

* Ядро распараллеливается через rayon, только если в нём ≥ `PAR_MIN_WORK = 2²⁰` умножений-сложений.
  Каждая задача получает ≥ `2¹⁶` MAC. Ниже порога пробуждение пула стоит дороже самой работы.
  С прежним порогом 2¹⁷ одно вычисление векторного поля `tiny` занимало 855 µs, а с теми же
  ядрами без rayon — 368 µs.
* В `tiny` параллельными оказываются только роллауты MPPI:
  `M·H·(2d_s + d_a)·d_hid = 128·4·72·128 ≈ 4.7M` MAC за итерацию, распределение по сэмплам.
  В `small` к ним добавляются крупные линейные слои.
* `kernels::set_parallel(bool)` — глобальный выключатель.

## Детерминизм

| Источник случайности | Поток RNG |
|---|---|
| инициализация параметров | `Rng::new(seed)` в `ParamStore` (свой для онлайн- и целевого хранилищ) |
| батчи обучения, шум CFM, `t`, шум плана | `Rng::stream(seed, 0x7EA1, 0)` |
| оценочная выборка | `Rng::stream(eval_seed, 0xE7A1, 0)` |
| шум сэмпла `m` на итерации `i` MPPI | `Rng::stream(seed, i, m)` |
| `X_0` декодера | `Rng::stream(seed, 0xF10, 0)` |

Каждый выходной элемент любого ядра считается одним потоком в фиксированном порядке суммирования.
Редукции MPPI последовательные. Поэтому результат бит-в-бит одинаков при любом числе потоков и
при `set_parallel(false)`. Это проверяет тест `mppi_reduces_energy_and_is_deterministic`.
Генератор — xoshiro256++ с инициализацией через SplitMix64; нормальное распределение —
Box–Muller.

## Производительность (`tiny`, 4 ядра x86-64 с AVX2/FMA/F16C)

| Стадия | Время | Объём работы |
|---|---:|---|
| TTT encode | 39 µs | 8 токенов |
| JEPA plan | 3.8 ms | роллаут π + 128 × 8 × 4 шагов world model |
| CFM decode | 5.0 ms | 32 вычисления DiT по 8 позиций (≈ 155 µs каждое) |
| **Всего** | **8.8 ms** | **113 запросов/с** на одном движке |

Рычаги латентности в порядке влияния:

1. `flow.solver.steps` и `solver` — decode линеен по NFE. `Euler` с 16 шагами вдвое дешевле `Heun`.
2. `planner.iterations` и `num_samples` — plan линеен по их произведению. `iterations = 0` оставляет
   только роллаут политики (`H` шагов одной траектории, пренебрежимо по сравнению с MPPI), но
   точность ниже (см. [training.md](training.md#оценка)).
3. `weight_dtype = F32` немного быстрее bf16 (нет конвертации), но вдвое больше памяти.

### Как профилировать

`perf` в среде разработки не было. Хорошо работает callgrind на release-сборке с отладочной
информацией:

```bash
valgrind --tool=callgrind --callgrind-out-file=cg.out ./target/release/<бинарь> …
callgrind_annotate cg.out | head -40
```

Именно так нашлись оба узких места. libm `tanhf` занимал 39% времени MPPI (исправлено
`fast_tanh`), а накладные расходы rayon на маленьких ядрах исправил порог `PAR_MIN_WORK`.
Сейчас профиль MPPI состоит в основном из самих FMA в `dot4` и обвязки линейного слоя.
